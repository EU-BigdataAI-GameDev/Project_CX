# 여동생 캐릭터 — 해킹 기능 기획

- 문서 버전: v1.0 (2026-07-25)
- 대상: 여동생 캐릭터(해킹) 담당 개발자, 적 AI 담당자, UI 담당자
- 목적: 여동생 캐릭터의 핵심 능력인 "해킹"을 (1) 근접한 적을 대상으로 한 그로기 유발 미니게임, (2) 단말기를 대상으로 한 문 개방 미니게임 두 갈래로 구현하기 위한 설계 문서. 코드 구현 이전 단계의 기획서이며, 실제 구현 시 이 문서를 갱신해 정합성을 유지한다.
- 자매 문서: `.claude/Plans/레벨 디자인 기획.md` (이하 "레벨 기획서") — 네이밍 컨벤션(`BP_HackTerminal_[번호]`, `BP_HackDoor_[번호]`), 3.5절 해킹 퍼즐 난이도/재시도 규칙, 3.7절 리슨 서버 권한 원칙과 반드시 정합성을 유지한다.

## 0. 코드베이스 조사 요약 (기획의 근거)

문서 작성 전 아래 항목을 조사했다. 이후 모든 설계 결정은 이 조사 결과를 기반으로 한다.

- **`ISideScrollingInteractable`** (`Source/Project_CX/Variant_SideScrolling/Interfaces/SideScrollingInteractable.h`): `UINTERFACE(MinimalAPI, NotBlueprintable)` + `virtual void Interaction(AActor* Interactor) = 0;` 하나만 정의된 최소 인터페이스. 현재 이 인터페이스를 구현하는 클래스는 `ASideScrollingNPC` (`Variant_SideScrolling/AI/SideScrollingNPC.h`) 하나뿐이며, 상호작용 시 즉시 넉백 임펄스를 주고 `DeactivationTime`(기본 3초) 동안 `bDeactivated` 플래그를 세우는 매우 단순한 패턴이다. **UI 프롬프트("해킹" 표시)를 띄우는 기존 구조는 없다.** 즉 상호작용 감지 자체는 재사용 가능하지만, 근접 시 프롬프트를 띄우는 부분은 신규로 만들어야 한다.
- **상호작용 입력/감지**: `ASideScrollingCharacter` (`Variant_SideScrolling/SideScrollingCharacter.h/.cpp`)에 `InteractAction`(`UInputAction*`), `InteractionRadius`(기본 200cm) 프로퍼티가 이미 존재한다. `SetupPlayerInputComponent()`에서 `EnhancedInputComponent->BindAction(InteractAction, ETriggerEvent::Triggered, this, &ASideScrollingCharacter::DoInteract)`로 바인딩되어 있고, `DoInteract()`(SideScrollingCharacter.cpp:189)는 `SweepSingleByObjectType`로 `ECC_Pawn`/`ECC_WorldDynamic` 채널에 대해 구체 스윕을 1회 수행해 **가장 먼저 맞은 히트 하나**만 `ISideScrollingInteractable`로 캐스트해 `Interaction()`을 호출한다. 즉 현재는 "가장 가까운" 것이 아니라 "스윕이 먼저 맞힌" 대상 단일 처리이며, 다중 후보 중 우선순위를 가리는 로직은 없다. 이는 3장에서 설계 결정이 필요한 지점이다.
- **Enhanced Input 애셋**: `Content/Variant_SideScrolling/Input/Actions/IA_Interact.uasset`와 `Content/Variant_SideScrolling/Input/IMC_SideScroller.uasset`가 이미 존재한다. 즉 **상호작용 입력 액션 자체는 이미 존재**하며(F 키 매핑 여부는 바이너리 애셋이라 텍스트 조사로 확정 불가 — 에디터에서 실제 키 바인딩 확인 필요), 신규로 만들 필요는 없다. 해킹 미니게임 내부의 방향키 입력(상/하/좌/우)은 별도 IA가 필요하며 신규 제안 대상이다.
- **적 AI / 그로기 상태**: `Variant_Combat/AI/CombatEnemy.h/.cpp`, `CombatAIController.h`, `CombatStateTreeUtility.h`를 조사했다. `ACombatEnemy`는 `ICombatDamageable`(`ApplyDamage`, `HandleDeath`, `ApplyHealing`)을 구현하고, `HandleDeath()`(CombatEnemy.cpp:222)에서 `GetCharacterMovement()->DisableMovement()`로 이동을 정지시키는 패턴을 사용한다. `ACombatAIController`는 `UStateTreeAIComponent`를 태워 StateTree로 행동을 구동한다. **"그로기/스턴" 상태에 대응하는 기존 조건·태스크·인터페이스는 코드베이스에 존재하지 않는다.** `CombatStateTreeUtility.h`에는 `FStateTreeCharacterGroundedCondition`, `FStateTreeComboAttackTask`, `FStateTreeChargedAttackTask`, `FStateTreeWaitForLandingTask`, `FStateTreeFaceActorTask`, `FStateTreeFaceLocationTask`, `FStateTreeSetCharacterSpeedTask`, `FStateTreeGetPlayerInfoTask`가 전부이며 그로기 관련 조건/태스크는 신규 제안해야 한다. 따라서 "5초 그로기"는 기존 컴포넌트에 얹는 것이 아니라 **신규 인터페이스(`IHackable` 등)를 만들어 `ACombatEnemy`(또는 그 하위 스파이더봇 블루프린트)가 구현하게 하고, StateTree 쪽에는 그로기 여부를 체크하는 조건 노드를 신규로 추가**하는 방향이 현실적이다.
- **UMG/위젯 관습**: `Variant_Combat/UI/CombatLifeBar.h`는 `UUserWidget`을 상속한 `UCLASS(abstract)` 베이스 클래스로, `BlueprintImplementableEvent`인 `SetLifePercentage(float)`, `SetBarColor(FLinearColor)`만 선언하고 실제 비주얼/바인딩은 블루프린트 서브클래스에서 구현하는 패턴이다. 이 위젯은 `ACombatEnemy`의 `UWidgetComponent`(월드 스페이스, 머리 위)에 붙는다. **"C++ 베이스 클래스(추상 로직) + BP 서브클래스(비주얼)" 패턴, 그리고 인게임 3D 위젯은 `UWidgetComponent`를 쓰는 관습**이 이미 확립되어 있으므로 해킹 미니게임 위젯도 이 패턴을 따른다.
- **적 배치 현황**: `Content/Project_CX/Characters/Enemy/SpiderBot/` 하위에 스켈레탈 메시/애님/피직스애셋/스켈레톤이 존재(`feat: add spiderbot in map1`, `feat: modified spiderbot size` 커밋). Map1에 배치된 스파이더봇이 "적 해킹" 기능의 1차 테스트 대상이 될 가능성이 높다.
- **CLAUDE.md 개발 조건**: C++ 우선(블루프린트 의존 최소화), 리슨 서버(호스트가 한 플레이어의 머신) 네트워킹 전제. 본 문서의 모든 판정 로직은 이 전제를 따른다.

## 1. 개요 / 목적

여동생 캐릭터의 정체성은 "전투 대신 해킹으로 문제를 해결한다"이다. 해킹 대상은 두 종류로 나뉜다.

| 대상 | 목적 | 결과 | UI 형태 |
|---|---|---|---|
| 적(Enemy) | 일시적으로 전투 불능화(그로기) | 5초 그로기 → 오빠가 무방비 상태의 적을 처치/제압 | 화면 일부에 작은 미니게임 패널 |
| 단말기(Terminal) | 다음 방으로 가는 문 개방 | 문 열림(`BP_HackDoor_[번호]`) | 화면 전체를 채우는 미니게임 패널, 미니게임 종류는 교체 가능 |

두 경우 모두 "근접 → F키로 상호작용 프롬프트 활성화 → F키 입력으로 해킹 시도 → 미니게임 → 성공/실패"라는 동일한 골격을 공유하지만, 미니게임의 판/연출 크기와 사후 처리(그로기 vs 문 개방)가 다르다. 따라서 설계는 "공통 상호작용/쿨타임 레이어" + "대상별 미니게임 레이어"로 분리한다.

## 2. 상호작용 감지 및 UI 프롬프트 설계

### 2.1 감지 범위

- 기존 `ASideScrollingCharacter::InteractionRadius`(기본 200cm) 및 `DoInteract()`의 구체 스윕 방식을 그대로 재사용한다. 여동생 캐릭터 클래스(신규 제안: `ASisterCharacter`, `ASideScrollingCharacter` 상속)에서 이 값을 필요 시 재정의할 수 있게 열어둔다.
- **설계 결정 (기본값, 추후 조정 가능)**: 해킹 대상 탐지 반경은 기존 `InteractionRadius` 200cm를 그대로 채택한다. 별도 수치 요구가 원본 기획에 없으므로 기존 값을 존중해 일관성을 유지한다.

### 2.2 상호작용 프롬프트 ("해킹" 표시)

- 현재 `ISideScrollingInteractable`/`DoInteract()`에는 프롬프트 UI가 없고 F키 입력 즉시 `Interaction()`을 호출하는 구조뿐이다. 원본 요구사항은 "근방에 대상이 있으면 F키가 활성화되며 '해킹' 표시가 뜬다"이므로, **매 틱 또는 낮은 주기 타이머로 감지 스윕을 미리 수행해 프롬프트를 띄우고, F키 입력 시에는 이미 캐시된 대상에 대해 해킹을 시작**하는 구조가 필요하다 (기존 `DoInteract()`처럼 키 입력 시점에만 스윕하는 방식으로는 "근방에 있으면 활성화된다"는 상시성을 표현할 수 없다).
- **신규 제안**: 여동생 캐릭터에 `UHackDetectionComponent`(가칭, `ActorComponent`)를 두고 일정 주기(기본 0.2초, 설계 결정·튜닝 가능)로 구체 오버랩을 수행해 `IHackable` 인터페이스(2.3 참고)를 구현하는 액터를 탐지한다. 탐지 결과가 바뀔 때만(대상 진입/이탈) 델리게이트를 브로드캐스트해 UI 위젯이 프롬프트를 토글하도록 한다. 매 틱 UI 갱신을 피해 불필요한 비용을 줄인다.
- 프롬프트는 `Variant_Combat`의 `CombatLifeBar`와 같은 패턴을 따라 대상 액터(적 또는 단말기)에 `UWidgetComponent`를 붙이거나, 화면 고정 HUD 위젯으로 "해킹 [F]" 텍스트를 띄운다. **설계 결정**: 적/단말기 각각의 머리 위·상단에 월드 스페이스 `UWidgetComponent`로 표시하는 쪽을 기본안으로 채택한다(레벨 기획서 3.8의 "출처가 명확한 광원/신호" 원칙과 톤이 맞고, 여러 대상이 동시에 화면에 있을 때 각각 표시가 가능해 원본의 "동시 근접" 케이스를 자연스럽게 처리하기 쉽다).

### 2.3 적/단말기 동시 근접 시 우선순위 (설계 결정)

원본 요구사항에 명시되지 않은 부분이므로 아래를 기본값으로 제안하고, 문서에 "설계 결정"임을 명시한다.

- 적과 단말기가 동시에 탐지 반경 안에 있는 경우, **거리가 더 가까운 대상 하나만 F키의 활성 대상으로 삼는다.** 동시에 여러 대상에 프롬프트를 띄우는 것(2.2)과, F키 입력 시 실제로 어떤 대상을 해킹할지 결정하는 것은 별개다 — 프롬프트는 반경 내 전 대상에 표시하되, F키를 눌렀을 때 실행되는 해킹은 최단거리 대상 하나로 한정한다.
- 동률(같은 거리)일 경우 적을 우선한다(전투 중 위협 제거가 더 시급하다는 판단).
- 이 우선순위 로직은 `UHackDetectionComponent`가 담당하며, 향후 밸런스 조정 시(예: "단말기 우선" 옵션) 컴포넌트 내부 정책만 바꾸면 되도록 별도 함수(`AActor* GetPriorityHackTarget() const`)로 분리해 캡슐화한다.

### 2.4 공용 인터페이스: `IHackable` (신규 제안)

`ISideScrollingInteractable`은 인자가 `AActor*` 하나뿐이라 "해킹 시작/그로기 처리/미니게임 종류 구분" 같은 해킹 고유 정보를 전달하기 부족하다. 기존 인터페이스를 억지로 재사용하기보다 신규 인터페이스를 별도로 만드는 편이 `SideScrollingInteractable`의 범용성을 해치지 않는다.

```cpp
// 신규 제안: Source/Project_CX/Variant_Hacking/Interfaces/HackableTarget.h
UINTERFACE(MinimalAPI, NotBlueprintable)
class UHackableTarget : public UInterface { GENERATED_BODY() };

class IHackableTarget
{
    GENERATED_BODY()
public:
    /** 해킹 시도 가능 여부 (쿨타임 중인 적 등은 false) */
    virtual bool CanBeHacked(AActor* Hacker) const = 0;

    /** 해킹 시도 시작 — 미니게임 위젯 클래스를 반환해 호출자가 스폰하게 한다 */
    virtual TSubclassOf<class UHackMinigameBase> GetHackMinigameClass() const = 0;

    /** 미니게임 결과를 통보받아 대상 자신의 사후 처리(그로기 부여/문 개방)를 수행 */
    virtual void OnHackResult(bool bSuccess, AActor* Hacker) = 0;
};
```

- 적용 대상: 적(그로기 부여 로직)과 단말기(문 개방 로직) 양쪽 모두 이 인터페이스를 구현한다. `ISideScrollingInteractable`은 그대로 두고 건드리지 않는다(기존 NPC 넉백 로직과 충돌 없음).

## 3. 해킹 쿨타임(3초) 처리

- **신규 제안**: `UHackerComponent`(가칭, `ActorComponent`, 여동생 캐릭터에 부착)가 쿨타임을 전담한다. 오빠 캐릭터에는 이 컴포넌트가 붙지 않으므로 캐릭터별 격리는 컴포넌트 부착 여부만으로 자연히 보장된다(오빠 클래스와 여동생 클래스를 `ASideScrollingCharacter`의 별도 서브클래스로 분리하는 것을 전제로 한다).
- 쿨타임은 `float LastHackAttemptTime` + `float HackCooldown = 3.0f`(설계 결정, 추후 조정 가능·`UPROPERTY(EditAnywhere)`로 노출) 비교로 처리한다. `GetWorld()->GetTimeSeconds() - LastHackAttemptTime < HackCooldown`이면 F키 입력을 무시(또는 프롬프트를 회색으로 비활성 표시)한다.
- **쿨타임 시작 시점**: 원본 요구사항 "상호작용 키를 누른 이후 3초"를 그대로 따라 **F키를 눌러 해킹을 시도한 시점**(미니게임 시작 시점)에 쿨타임을 시작한다. 성공/실패와 무관하게 시도 자체가 쿨타임을 소모한다.
- **리슨 서버 권한**: 쿨타임 자체는 즉시 반응성이 중요한 로컬 UI 상태이므로 클라이언트 예측(로컬에서 즉시 반영) 후, 실제 해킹 판정 시작 요청은 서버(호스트)로 RPC(`Server_RequestBeginHack`)를 보내 서버가 쿨타임을 재검증한다. 서버가 최종 권위를 가지며, 클라이언트 표시는 어디까지나 예측 UI로 취급한다(레벨 기획서 3.4/3.7이 채택한 "판정은 호스트 권한" 원칙과 동일선상).
- 리슨 서버 모델 특성상 호스트가 아닌 클라이언트가 여동생을 조작하는 세션에서는, `UHackerComponent`를 `Replicated`로 표시하고 쿨타임 종료 시각(`LastHackAttemptTime`)을 서버가 소유·복제해 클라이언트 측 위·변조나 오차 누적을 막는다.

## 4. 적 해킹 미니게임

### 4.1 흐름

1. 여동생이 F키 입력 → `IHackableTarget::CanBeHacked()` 확인(쿨타임, 대상이 이미 그로기 상태인지 등) → 통과 시 서버에 해킹 시작 요청.
2. 서버 승인 시 미니게임 위젯(적용 클래스는 `GetHackMinigameClass()`가 지정)을 클라이언트에서 스폰해 표시. 방향키 6개를 랜덤 순서로 생성해 패널에 나열한다.
3. 시간 제한 내 플레이어가 방향키를 순서대로 입력.
4. 성공: `Hacked!` 표시 → 패널 닫힘 → 서버에 성공 결과 통보 → 대상의 `OnHackResult(true, Hacker)` 호출 → 그로기 부여(4.3).
5. 실패(시간 초과 또는 오입력): `Failed` 표시 → 패널 닫힘 → `OnHackResult(false, Hacker)` 호출(그로기 없음). 레벨 기획서 3.5 "무제한 재시도, 소프트락 금지" 원칙에 따라 실패해도 쿨타임 종료 후 즉시 재시도 가능해야 한다.

### 4.2 미니게임 파라미터 (설계 결정, 전부 `UPROPERTY(EditAnywhere)`로 노출해 밸런싱 가능하게 한다)

| 파라미터 | 기본값(제안) | 비고 |
|---|---|---|
| 방향키 시퀀스 길이 | 6개 (원본 요구사항 고정값) | 상/하/좌/우 중 랜덤 |
| 제한 시간 | 4.0초 | 초심자 튜토리얼(Map1)에서는 별도 배율(예: ×1.5)을 두는 것을 권장 — 레벨 기획서 2.1의 Map1 "튜토리얼" 포지션과 정합 |
| 오입력 처리 | 즉시 실패 | 원본 요구사항("잘못 눌렀을 경우 Failed")을 그대로 따름. 유예(1회 실수 허용) 여부는 미도입 — 필요 시 별도 파라미터로 확장 가능하게 설계만 열어둠 |
| 재시도 | 쿨타임(3초) 종료 후 즉시 가능, 횟수 제한 없음 | 레벨 기획서 3.5 원칙 |

### 4.3 성공 시 그로기 상태 연동 (StateTree)

- 0장 조사 결과, 기존 `CombatStateTreeUtility.h`에는 그로기/스턴에 대응하는 조건·태스크가 없다. 따라서 다음을 **신규 제안**한다.
  - `ACombatEnemy`(또는 스파이더봇 등 하위 블루프린트)가 `IHackableTarget`을 구현하고, `OnHackResult(true, ...)`에서 `bool bIsGroggy` 플래그를 세우고 `FTimerHandle GroggyTimer`로 5초(설계 결정, `UPROPERTY(EditAnywhere) float GroggyDuration = 5.0f`) 후 해제한다. 그로기 중에는 `HandleDeath()`가 이미 사용하는 패턴과 동일하게 `GetCharacterMovement()->DisableMovement()` 또는 이동 속도를 0으로 만드는 방식으로 이동을 정지시키고, 공격 판정(`ICombatAttacker`)을 일시적으로 비활성화한다(구체적으로는 `bIsAttacking`류 플래그를 참조하는 공격 개시 함수 초입에서 `bIsGroggy`면 조기 반환하도록 가드를 추가).
  - StateTree 쪽에는 `FStateTreeEnemyIsGroggyCondition`(신규 제안, `FStateTreeConditionCommonBase` 상속, `CombatStateTreeUtility.h`의 `FStateTreeCharacterGroundedCondition`과 동일한 패턴)을 추가해, 그로기 중에는 공격/추격 상태로 전이하지 않고 별도의 "Groggy" 상태(무방비 애니메이션 루프)에 머무르도록 StateTree 그래프에서 분기시킨다. 이 조건 노드와 StateTree 애셋 자체의 그래프 수정은 AI 담당자와 협의가 필요하다.
  - 그로기 종료 시 원래 상태(순찰/추격)로 자연 복귀하도록 타이머 콜백에서 `bIsGroggy = false`로 되돌리기만 하면, StateTree는 조건 재평가로 알아서 이전 분기로 돌아간다(별도 강제 상태 전이 코드 불필요).
- **리슨 서버 권한**: 그로기 판정(미니게임 성공/실패)과 `bIsGroggy`/`GroggyTimer`는 서버(호스트) 전용으로 처리하고 `bIsGroggy`는 `Replicated` 프로퍼티로 클라이언트에 복제한다. 미니게임 자체의 입력(방향키 시퀀스 진행)은 로컬 클라이언트에서 즉시 반응하도록 처리하되, 최종 성공/실패 판정은 서버로 결과를 보내 서버가 확정한다(클라이언트가 결과를 임의로 조작해 그로기를 강제할 수 없도록).

## 5. 단말기 해킹 미니게임

### 5.1 전체화면 패널

- 적 해킹과 달리 화면을 꽉 채우는 풀스크린 위젯으로 표시한다. `CombatLifeBar`가 인게임 3D `UWidgetComponent`인 것과 달리, 이 패널은 HUD 레이어(`APlayerController::AddToViewport` 또는 `SideScrollingUI`류 HUD 위젯의 자식으로 추가)로 띄운다. 조사 결과 `Variant_SideScrolling/UI/SideScrollingUI.h`가 기존 HUD 위젯 진입점이므로, 신규 해킹 패널도 이 위젯 체계에 자식 위젯으로 편입하거나 별도 최상위 위젯으로 추가하는 두 방식 중 팀 협의로 정한다(본 문서는 방식을 강제하지 않음).

### 5.2 교체 가능한 미니게임 구조 (핵심 요구사항)

원본 요구사항이 명시한 "여러 미니게임 기믹을 추가할 예정이므로 교체 가능해야 한다"를 만족시키기 위해, **추상 베이스 위젯 + 액터가 클래스 참조로 미니게임을 지정하는 구조**를 제안한다. `CombatLifeBar`가 "C++ 추상 베이스 + BP 서브클래스로 비주얼/세부로직 구현" 패턴을 이미 쓰고 있으므로 동일한 관습을 따른다.

```cpp
// 신규 제안: Source/Project_CX/Variant_Hacking/UI/HackMinigameBase.h
UCLASS(abstract)
class UHackMinigameBase : public UUserWidget
{
    GENERATED_BODY()
public:
    /** 미니게임 결과 델리게이트. 성공 여부를 브로드캐스트 */
    DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnMinigameFinished, bool, bSuccess);
    UPROPERTY(BlueprintAssignable)
    FOnMinigameFinished OnMinigameFinished;

    /** 미니게임 시작 — 파라미터(제한시간 등)는 서브클래스가 자유롭게 해석 */
    UFUNCTION(BlueprintCallable, Category="Hacking")
    virtual void StartMinigame(AActor* HackTarget, AActor* Hacker) { /* 기본 구현: 서브클래스에서 override */ }

    /** 서브클래스가 성공/실패를 확정할 때 호출 */
    UFUNCTION(BlueprintCallable, Category="Hacking")
    void FinishMinigame(bool bSuccess) { OnMinigameFinished.Broadcast(bSuccess); }
};
```

- 방향키 시퀀스 미니게임(적 해킹용, 4장)도 사실 이 베이스를 공유하도록 설계하면 향후 "적에게도 다른 미니게임을 붙이고 싶다"는 확장 요구에 대응하기 쉽다. 다만 원본 요구사항은 적 해킹의 미니게임 종류를 방향키 시퀀스로 고정했으므로, 4장의 미니게임은 `UHackMinigameBase`의 첫 번째 구체 서브클래스(`UHackMinigame_DirectionSequence`, 신규 제안)로 구현하고, 단말기는 이 서브클래스를 포함한 여러 서브클래스 중 하나를 애셋 참조로 지정해 재사용하는 그림을 권장한다.
- 단말기 액터 측 설계:

```cpp
// 신규 제안: Source/Project_CX/Variant_Hacking/Gameplay/HackTerminal.h
UCLASS(abstract)
class AHackTerminal : public AActor, public IHackableTarget, public ISideScrollingInteractable
{
    GENERATED_BODY()
protected:
    /** 이 단말기가 사용할 미니게임 위젯 클래스 — 단말기별로 다른 기믹을 꽂아 넣을 수 있는 지점 */
    UPROPERTY(EditAnywhere, Category="Hacking")
    TSubclassOf<class UHackMinigameBase> MinigameClass;

    /** 해킹 성공 시 열릴 문 액터 참조 */
    UPROPERTY(EditAnywhere, Category="Hacking")
    AActor* LinkedDoor; // 또는 신규 제안 인터페이스 IHackDoor
public:
    virtual TSubclassOf<UHackMinigameBase> GetHackMinigameClass() const override { return MinigameClass; }
    virtual void OnHackResult(bool bSuccess, AActor* Hacker) override; // 성공 시 LinkedDoor 개방 처리
};
```

- 즉 **"단말기 액터가 `TSubclassOf<UHackMinigameBase>` 프로퍼티로 어떤 미니게임을 스폰할지 지정"**하는 구조가 교체 가능성의 핵심이다. 레벨 디자이너는 블루프린트 디테일 패널에서 드롭다운으로 미니게임 종류만 바꾸면 되고, 신규 미니게임 기믹을 추가할 때는 `UHackMinigameBase`를 상속한 새 위젯(BP 또는 C++)만 추가하면 기존 단말기 액터 코드를 건드릴 필요가 없다(개방-폐쇄 원칙).
- 레벨 기획서의 `BP_HackTerminal_[번호]` 네이밍 규칙과 정합: `AHackTerminal`의 블루프린트 서브클래스를 맵별로 `BP_HackTerminal_01`, `BP_HackTerminal_02`처럼 배치하고, 각 인스턴스가 `MinigameClass`만 다르게 지정하는 식으로 운용한다.

### 5.3 문 개방과의 연동

- 성공 시 `OnHackResult(true, Hacker)`에서 `LinkedDoor`(레벨 기획서 네이밍상 `BP_HackDoor_[번호]`) 개방 로직을 호출한다. 문 액터 자체의 개방 애니메이션/콜리전 처리는 본 문서 범위 밖이며 레벨 기획서 3.5(문/게이트 네이밍, 재시도 규칙)를 따른다.
- 실패 시 패널만 닫히고 문은 열리지 않는다. 레벨 기획서 3.5 원칙에 따라 무제한 재시도 가능해야 하므로 실패가 소프트락으로 이어지지 않는다.

## 7. 네트워킹/리플리케이션 고려사항 (리슨 서버 기준)

CLAUDE.md의 "리슨 서버 네트워킹" 전제(호스트가 곧 한 플레이어의 머신)를 따른다.

- **권한 분리 원칙**: 미니게임의 "입력 반응성"(방향키 하이라이트, 타이머 UI 갱신 등)은 로컬 클라이언트에서 즉시 처리해 지연 없는 조작감을 준다. 반면 **"성공/실패 최종 판정", "쿨타임 종료 시각", "그로기 부여/해제", "단말기 문 개방"은 전부 서버(호스트) 권위로 처리**한다.
- **RPC 흐름 (제안)**:
  1. 클라이언트(여동생) → 서버: `Server_RequestBeginHack(AActor* Target)` — 쿨타임/거리/`CanBeHacked()` 서버 재검증.
  2. 서버 → 해당 클라이언트: 승인 시 미니게임 시작을 위한 시드값(방향키 시퀀스 생성 시드 등)을 전달해 클라이언트-서버 간 시퀀스 불일치를 막는다. 시퀀스 자체는 서버가 생성해 내려주는 편이 부정행위 방지 측면에서 안전하다.
  3. 클라이언트: 로컬에서 미니게임 진행, 완료 시 결과를 서버로 전송 `Server_ReportHackResult(bool bSuccess)`.
  4. 서버: 결과를 검증(제한시간 초과 여부 등 서버 측에서도 이중 체크 권장) 후 `IHackableTarget::OnHackResult()` 호출 → 그로기 부여/문 개방을 서버에서 수행하고, 결과를 관련 클라이언트에 복제(`Replicated` 프로퍼티 또는 멀티캐스트 RPC로 `Hacked!`/`Failed` 연출 트리거).
- **리슨 서버 특성 고려**: 호스트 자신이 여동생을 조작하는 경우 클라이언트=서버이므로 지연이 사실상 없다. 원격 클라이언트가 여동생을 조작하는 경우에는 2~3단계에서 왕복 지연(RTT)이 발생하므로, 미니게임 제한 시간(4.2의 4.0초)에는 이 지연을 흡수할 최소한의 여유(예: 서버 판정 시 클라이언트 보고 시각 기준 200ms 정도의 유예)를 두는 것을 권장한다(레벨 기획서 3.4가 협동 트리거에 "여유 있는 트리거 볼륨"을 둔 것과 같은 취지).
- **치트 방지 관점**: 그로기/문 개방처럼 게임 진행에 영향을 주는 결과는 반드시 서버가 최종 승인해야 하며, 클라이언트가 보낸 `bSuccess` 값을 그대로 신뢰하지 않는다(가능하다면 서버가 방향키 입력 각각을 검증하거나, 최소한 서버가 독립적으로 생성한 시퀀스와 클라이언트가 보고한 입력 로그를 대조한다). 포트폴리오 성격상 완전한 부정행위 방지까지 과설계할 필요는 없지만, 구조상 "서버가 최종 권한을 가진다"는 원칙만은 지킨다.

## 8. 향후 확장 여지

- **신규 미니게임 기믹 추가 시**: `UHackMinigameBase`를 상속하는 새 위젯 클래스(C++ 또는 BP)를 추가하고, 해당 단말기(`AHackTerminal`)의 `MinigameClass` 프로퍼티를 새 클래스로 지정하기만 하면 된다. `AHackTerminal`, `IHackableTarget`, 문 개방 로직은 전혀 수정할 필요가 없다(5.2절 개방-폐쇄 원칙).
- **적 해킹에도 다른 미니게임을 붙이고 싶어질 경우**: `IHackableTarget::GetHackMinigameClass()`가 이미 클래스 참조를 반환하는 구조이므로, 적 종류별로 다른 미니게임 클래스를 지정하는 것도 동일한 방식으로 확장 가능하다(예: 근접 로봇은 방향키 시퀀스, 원거리 로봇은 다른 미니게임).
- **난이도 곡선과의 연동**: 레벨 기획서 3.5 "맵1(단일 단계) → 맵2~3(2단계 조합) → 맵4(다단계+시간제한/방해요소)" 난이도 곡선은, 단말기 쪽은 `MinigameClass` 교체로, 적 해킹 쪽은 4.2 파라미터(제한시간, 시퀀스 길이 등을 맵별로 오버라이드)로 대응할 수 있다. 다만 원본 요구사항은 적 해킹의 시퀀스 길이를 "6개"로 고정했으므로, 난이도를 올리려면 시퀀스 길이보다는 제한시간을 조이는 쪽을 권장한다.
- **방해 요소(레벨 기획서 3.5의 "맵4: 시간 제한 또는 방해 요소")**: `UHackMinigameBase` 서브클래스 내부에서 자유롭게 구현 가능하다(예: 화면 흔들림, 가짜 입력 힌트 등). 베이스 클래스가 `StartMinigame`/`FinishMinigame`만 강제하므로 내부 구현은 완전히 자유롭다.

## 9. 완료 체크리스트

### 9.1 공통 상호작용/쿨타임

- [ ] `IHackableTarget` 인터페이스가 정의되어 있고 적/단말기 양쪽이 구현한다.
- [ ] 근접 시 F키가 활성화되고 "해킹" 프롬프트가 표시된다 (`UHackDetectionComponent` 또는 대응 구현).
- [ ] 적/단말기 동시 근접 시 2.3의 우선순위(최단거리, 동률 시 적 우선) 정책이 적용되어 있다(또는 팀에서 재확정한 정책으로 갱신).
- [ ] F키 입력 후 3초간 재상호작용이 불가능하고, 쿨타임 판정이 서버(호스트) 권한으로 처리된다.
- [ ] 오빠 캐릭터에는 해킹 쿨타임/컴포넌트가 붙지 않는다(캐릭터 간 능력 분리 확인).

### 9.2 적 해킹

- [ ] 해킹 시도 시 6개 랜덤 방향키 시퀀스 미니게임 패널이 뜬다.
- [ ] 시간 제한 내 정확한 순서 입력 시 `Hacked!` 표시와 함께 대상이 5초 그로기 상태가 된다.
- [ ] 시간 초과 또는 오입력 시 `Failed` 표시와 함께 패널이 닫히고, 그로기는 부여되지 않는다.
- [ ] 그로기 중인 적은 StateTree 상에서 공격/추격 행동으로 전이하지 않는다(신규 그로기 조건 노드 반영).
- [ ] 그로기 종료 후 적이 정상 상태(순찰/추격)로 자연 복귀한다.
- [ ] 그로기 부여/해제가 서버 권한으로 처리되고 클라이언트에 정상 복제된다.

### 9.3 단말기 해킹

- [ ] 단말기 해킹 시 미니게임 패널이 화면 전체를 채워 표시된다.
- [ ] 단말기 액터(`AHackTerminal` 또는 대응 구현)가 `TSubclassOf<UHackMinigameBase>` 프로퍼티로 미니게임 종류를 지정 가능하다.
- [ ] 신규 미니게임 클래스를 추가할 때 `AHackTerminal`/`IHackableTarget`/문 개방 로직을 수정하지 않고도 꽂아 넣을 수 있다(개방-폐쇄 원칙 검증).
- [ ] 성공 시 연결된 문(`BP_HackDoor_[번호]`)이 열리고, 실패 시 무제한 재시도가 가능하다(레벨 기획서 3.5 정합).
- [ ] 네이밍이 레벨 기획서 3.1(`BP_HackTerminal_[번호]`, `BP_HackDoor_[번호]`)을 따른다.

### 9.4 네트워킹

- [ ] 해킹 시작 요청/결과 보고가 RPC를 통해 서버로 전달되고, 서버가 최종 성공/실패를 승인한다.
- [ ] 원격 클라이언트가 여동생을 조작하는 경우에도 RTT 지연을 고려한 유예가 반영되어 있다(7장 참고).
- [ ] 그로기 상태, 쿨타임 종료 시각 등 게임플레이에 영향을 주는 상태가 `Replicated`로 선언되어 있다.
