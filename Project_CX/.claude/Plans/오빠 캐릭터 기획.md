- 문서 버전: v1.0 (2026-08-23)

## 0. 코드베이스 조사 요약 (기획의 근거)

문서 작성 전 아래 항목을 조사했다. 이후 모든 설계 결정은 이 조사 결과를 기반으로 한다.

- **`ACombatCharacter`** (`Source/Project_CX/Variant_Combat/CombatCharacter.h/.cpp`): 기존 콤뱃 샘플의 플레이어 캐릭터로, **근접 콤보(`ComboAttack`)와 차지 공격(`ChargedAttack`) 전용**으로 짜여 있다. `bIsAttacking` 플래그 + `OnAttackMontageEnded` 델리게이트(`AttackMontageEnded`, CombatCharacter.cpp:221)로 공격 중 재입력을 "캐시(`CachedAttackInputTime`)해뒀다가 몽타주가 자연 종료된 후 재생"하는 방식이며, **몽타주를 도중에 강제 중단(`Montage_Stop`)하는 로직은 어디에도 없다** — 즉 "회피가 공격을 즉시 캔슬한다"는 요구사항에 대응하는 기존 패턴이 코드베이스에 없으므로 이 부분은 신규 설계가 필요하다. `TakeDamage()` 오버라이드(CombatCharacter.cpp:381)는 `CurrentHP <= 0.0f`일 때만 조기 반환하는 단순 가드 구조이며, 이 자리에 무적 프레임 가드를 추가하는 것이 자연스러운 확장 지점이다. **원거리(사격) 무기 패턴은 `Variant_Combat` 전체를 검색해도 존재하지 않는다**(`Fire`/`Gun`/`Weapon`/`Projectile`/`Ranged` grep 결과 0건) — 레일건은 완전 신규 설계 대상이다.
- **카메라 불일치**: `ACombatCharacter`는 `CameraBoom`(`bUsePawnControlRotation = true`) + `FollowCamera`로 구성된 **3인칭 오빗 카메라**를 쓴다(CombatCharacter.cpp:33-44). 반면 레벨 기획서 3.3은 "모든 맵은 `SideScrollingCameraManager`를 기반으로 확장해 사용, 맵마다 카메라 로직을 새로 짜지 않는다"를 필수 규칙으로 못박고 있다. 따라서 **`ACombatCharacter`를 그대로 상속하는 것은 이 프로젝트의 카메라 컨벤션과 충돌**한다. 여동생 기획서도 동일한 이유로 `ASideScrollingCharacter`를 베이스로 채택했으므로(여동생 기획서 6장 `ASisterCharacter : ASideScrollingCharacter`), 오빠 캐릭터도 같은 베이스를 채택하는 것이 카메라 일관성과 남매 캐릭터 쌍의 대칭성 양쪽에 부합한다.
- **`ASideScrollingCharacter`** (`Variant_SideScrolling/SideScrollingCharacter.h`): `MoveAction`/`JumpAction`/`DropAction`/`InteractAction` Enhanced Input 바인딩, `InteractionRadius`(200cm), 코요테 타임/월 점프/소프트 콜리전 등 이 프로젝트의 실제 사이드뷰 이동 로직을 담은 클래스다. 카메라는 오빗 없이 단일 `UCameraComponent`만 두어 `SideScrollingCameraManager`와 궁합이 맞는다.
- **`ICombatAttacker` / `ICombatDamageable`** (`Variant_Combat/Interfaces/`): `ACombatCharacter`(플레이어)와 `ACombatEnemy`(적) **양쪽 모두** 이 두 인터페이스를 대칭적으로 구현한다(공격자↔피격자가 같은 채널을 공유). `ICombatDamageable::ApplyDamage/HandleDeath/ApplyHealing`은 공격 방식(근접/원거리)에 무관한 범용 피격 인터페이스이므로 오빠 캐릭터도 그대로 구현해 재사용하는 것이 타당하다 — 그래야 기존 `CombatEnemy`의 공격(및 향후 원거리 로봇)이 수정 없이 오빠에게 데미지를 적용할 수 있다. 반면 `ICombatAttacker`의 세 함수(`DoAttackTrace`/`CheckCombo`/`CheckChargedAttack`)는 근접 콤보·차지 공격 전용 시그니처라 단발 히트스캔 레일건에는 맞지 않는다 — 억지로 구현하면 콤보 섹션 점프 같은 불필요한 개념이 끼어든다. **설계 결정**: `ICombatDamageable`만 구현하고, 발사 로직은 자체 함수로 새로 둔다(5장 참고).
- **AnimNotify 관습**: `AnimNotify_DoAttackTrace`(Variant_Combat)는 `Cast<ICombatAttacker>(MeshComp->GetOwner())`로 인터페이스를 캐스팅해 호출하는 패턴, `AnimNotify_EndDash`(`Variant_Platforming/Animation/AnimNotify_EndDash.h`)는 `Cast<APlatformingCharacter>`로 구체 클래스를 캐스팅해 `EndDash()`를 직접 호출하는 패턴이다. 두 방식 모두 "몽타주의 특정 프레임에서 AnimNotify가 게임플레이 함수를 호출한다"는 동일한 관습을 공유한다. **`AnimNotify_EndDash`는 회피(구르기/돌진류 상태 종료) 설계의 직접적 선례**다: `APlatformingCharacter`는 `bIsDashing`/`bHasDashed` 플래그로 대시 상태를 관리하고(`PlatformingCharacter.h:147-148`), `MultiJump()`는 `if(bIsDashing) return;`로 대시 중 다른 액션을 차단하며(PlatformingCharacter.cpp:106), 대시 종료는 몽타주 끝의 `AnimNotify_EndDash`가 `EndDash()`를 호출해 `bIsDashing = false`로 되돌린다. 이 "상태 플래그 + AnimNotify로 상태 종료" 골격을 회피 시스템에 그대로 차용한다.
- **Enhanced Input 애셋**: `Content/Input/Actions/`에 `IA_Jump`/`IA_Move`/`IA_Look`/`IA_MouseLook`(기본), `Content/Variant_Combat/Input/Actions/`에 `IA_ComboAttack`/`IA_ChargedAttack`(근접 콤보용, 좌클릭이 아니라 콤보/차지 전용 의미 부여됨), `Content/Variant_Platforming/Input/Actions/IA_Dash`, `Content/Variant_SideScrolling/Input/Actions/`에 `IA_Interact`/`IA_Drop`/`IA_Mover`가 존재한다. **좌클릭 공격, 우클릭/좌쉬프트 회피에 대응하는 입력 액션은 존재하지 않는다** — 전부 신규 제작 대상이다. `ACombatCharacter::SetupPlayerInputComponent()`(CombatCharacter.cpp:461-472)는 `LookAction`과 `MouseLookAction` 두 개의 별도 IA를 동일한 `Look` 함수에 바인딩하는 패턴을 쓰는데, 이는 "하나의 논리 입력에 여러 물리 키를 매핑"하는 방식의 실제 선례이므로 회피(좌쉬프트+우클릭)의 이중 바인딩 설계에 참고할 수 있다.
- **적 배치 현황**(레벨 기획서 3.6 교차 확인): 근거리 로봇은 좁은 통로/오빠 전용 구간에 인카운터당 2~3마리, 원거리 로봇은 개활지에 배치되며 "반드시 플레이어가 인지할 수 있는 조준 레이저/조명 신호"를 켜는 것이 필수 규칙이다. 이는 2장의 히트스캔 채택 판단과 7장의 협동 엄호 설계에 직접 반영한다.
- **CLAUDE.md 개발 조건**: C++ 우선(블루프린트 의존 최소화), 리슨 서버(호스트가 곧 한 플레이어의 머신) 네트워킹 전제. 본 문서의 모든 판정 로직은 이 전제를 따른다.

## 1. 개요 / 목적

오빠 캐릭터의 정체성은 "힘과 전투로 정면을 돌파한다"이다. 여동생이 해킹(그로기/문 개방)으로 문제를 우회한다면, 오빠는 원거리 화력(레일건)과 반응형 회피(저스트 회피)로 정면 위협을 직접 처리한다.

| 항목 | 오빠 | 여동생 |
|---|---|---|
| 핵심 능력 | 전투(레일건) / 회피 | 해킹(그로기 미니게임 / 문 개방 미니게임) |
| 담당 구간(레벨 기획서 3.4) | 오빠 전용 구간(적/장애물 다수, 힘 필요) | 여동생 전용 구간(좁은 틈, 감시 카메라 회피, 단말기) |
| 취약 타이밍 | 장전(2초) 중 공격 불가 | 해킹 중 무방비(레벨 기획서 3.5) |
| 상호 엄호 | 해킹 중인 여동생 주변 적 제거(7장) | 오빠가 장전/회피 쿨타임인 순간을 그로기로 시간 벌어줌(7장) |

두 캐릭터 모두 "혼자서는 못 뚫고, 서로가 서로의 약점을 메꿔야 진행 가능"하다는 레벨 기획서 3.4의 협동 원칙을 공유한다.

## 2. 무기/공격 설계

### 2.1 레일건 컨셉

- 이름: 휴대용 레일건(portable railgun). 비주얼 톤은 미래지향적 레이저 권총 — 슬럼가의 "고장 나서 깜빡이는 네온"(레벨 기획서 3.8)과 대비되는, 오빠가 소지한 유일하게 "제대로 작동하는" 첨단 장비로 연출하면 캐릭터성(힘/기술의 균형)을 살릴 수 있다.
- 공격키: **마우스 좌클릭**.
- 입력 트리거: `ACombatCharacter::ComboAttackAction`이 `ETriggerEvent::Started`(1회 눌림당 1회 발동, 홀드 연사 아님)로 바인딩된 선례(CombatCharacter.cpp:468)를 그대로 채택한다. 즉 **클릭 1회 = 발사 1회**이며 홀드로 자동 연사되지 않는다. 이 자체가 자연스러운 연사 속도 제한 역할을 겸한다(원본 요구사항에 연사 속도 제한이 없으므로 별도 쿨타임을 추가로 얹지 않는다 — 과설계 방지).

### 2.2 탄창 / 장전

- 탄창 용량: **30발** (원본 고정값).
- 30발 모두 소모 시 **에너지 충전 방식 장전**이 자동으로 시작된다. 원본 요구사항에 수동 장전 키가 없으므로, 탄약이 0이 되는 순간(또는 탄약 0인 상태에서 발사를 시도한 순간) 자동으로 `StartReload()`가 트리거되는 구조로 설계한다(수동 리로드 입력은 신규로 만들지 않는다 — 과설계 방지, 원본에 없는 기능 추가 금지).
- 장전 딜레이: **2초** (원본 고정값). 장전 중에는 좌클릭 입력을 무시한다(공격 불가, 원본 요구사항).
- **설계 결정 (기본값, 추후 조정 가능)**: 장전 중에도 이동은 가능하게 한다. 원본 요구사항이 장전 중 이동 제한을 언급하지 않았고, 회피 시스템과의 시너지(장전 중에도 위협을 감지하면 최소한 자리를 이동할 수 있어야 한다)를 위해 이동은 열어둔다.

### 2.3 발사 판정 방식: 히트스캔 채택

원본 요구사항에 없는 부분이므로 아래를 **설계 결정(기본값, 추후 조정 가능)**으로 제안한다.

**히트스캔(라인 트레이스)을 채택**하고, 프로젝타일(발사체 액터) 방식은 채택하지 않는다. 근거:

1. **무기 컨셉과의 정합**: "레이저" 권총은 통상 순간 도달(빛의 속도) 판정이 자연스럽다. 탄속이 있는 프로젝타일은 "레일건 레이저"라는 비주얼 컨셉과 어긋난다.
2. **적 타입별 상성**: 레벨 기획서 3.6에 따르면 원거리 로봇은 "반드시 조준 레이저/조명 신호로 텔레그래프"되므로, 플레이어가 이를 인지하고 반응(회피 또는 선제 사격)하는 것이 핵심 상호작용이다. 오빠의 사격 자체가 프로젝타일 탄속으로 지연되면 "적의 텔레그래프에 반응해 즉시 카운터"하는 판타지가 약해진다. 근접 로봇 상대로도 좁은 통로(레벨 기획서 3.2, 통로 폭 120~250cm)에서는 판정 지연이 체감 프러스트레이션으로 이어지기 쉽다.
3. **회피 시스템과의 역할 분리**: 이 게임의 회피/무적 판정(3장)은 "적의 공격"을 피하는 데 집중되어야 한다. 플레이어 자신의 탄환에도 탄속·회피 가능성을 부여하면 판정이 이중으로 복잡해진다(적이 플레이어 탄을 피하는 개념은 원본 요구사항에 없다).
4. **네트워킹 단순성**: 리슨 서버 환경에서 프로젝타일은 스폰/이동/충돌을 매 틱 복제해야 하는 반면, 히트스캔은 발사 순간의 트레이스 결과만 서버가 확정하면 되어 리플리케이션 비용이 훨씬 낮다(6장).

구현은 `ACombatCharacter::DoAttackTrace`(근접 스피어 스윕 → `ICombatDamageable::ApplyDamage` 호출, CombatCharacter.cpp:243-286)의 **"트레이스 후 `ICombatDamageable`에 데미지 적용"이라는 뼈대만 차용**하되, 스피어 스윕 대신 원거리 라인 트레이스로 교체한다.

- **설계 결정(기본값)**: 사거리 3000cm, 1샷당 데미지 1.0. 데미지 수치는 `ACombatCharacter`의 기존 `MeleeDamage = 1.0f`(MaxHP 5.0 기준, CombatCharacter.h:74,112)와 동일 스케일을 유지해 기존 밸런스 단위와 충돌하지 않게 한다(실제 값은 적 HP 설계 확정 후 조정).
- 발사 타이밍은 `AnimNotify_DoAttackTrace`의 관습을 그대로 차용한 **신규 제안 `UAnimNotify_FireRailgun`**이 몽타주의 발사 프레임에서 `BrotherCharacter->FireRailgun()`을 호출하는 방식으로 애니메이션과 판정을 동기화한다(총구 이펙트/반동과 실제 히트 판정 프레임을 맞추기 위함).

### 2.4 탄약 UI

- 탄창 잔여 수(예: `24/30`)와 장전 중 표시가 필요하다. 여동생 기획서가 `CombatLifeBar`의 "C++ 추상 베이스 클래스(로직) + BP 서브클래스(비주얼)" 패턴을 따르기로 한 것과 동일한 관습을 채택한다.
- **신규 제안**: `URailgunAmmoWidget`(`UUserWidget` 상속, `UCLASS(abstract)`)에 `BlueprintImplementableEvent SetAmmoCount(int32 Current, int32 Max)`, `SetReloading(bool bIsReloading)`을 선언하고 비주얼은 BP 서브클래스가 구현한다.
- 탄약은 "적/단말기 등 월드 대상에 종속된 정보"가 아니라 "플레이어 개인 상태"이므로, 여동생 기획서의 해킹 프롬프트(월드 스페이스 `UWidgetComponent`, 대상 머리 위)와 달리 **화면 고정 HUD**로 배치한다. `Variant_SideScrolling/UI/SideScrollingUI.h`가 기존 HUD 진입점이므로 이 위젯 체계의 자식으로 편입하는 것을 권장한다(여동생 기획서 5.1과 동일한 결론).

### 2.5 리로드 상태 머신

`bIsReloading` 플래그 + `FTimerHandle ReloadTimer`(2.0초, `UPROPERTY(EditAnywhere)`로 노출)로 처리한다.

1. `FireRailgun()`에서 탄약을 1 소모한 후 `CurrentAmmo <= 0`이면 즉시 `StartReload()` 호출.
2. `StartReload()`: `bIsReloading = true`, 장전 몽타주 재생, `ReloadTimer` 2초 세팅.
3. 타이머 만료 → `FinishReload()`: `CurrentAmmo = MaxAmmo`, `bIsReloading = false`.
4. 장전 중 좌클릭 입력은 `bIsReloading` 가드로 조기 반환(무시).
5. **회피로 장전이 취소된 경우**(3.3 참고)에도 `CurrentAmmo`는 0으로 유지된다 — 이후 좌클릭(발사 시도) 시 `CurrentAmmo <= 0` 조건이 그대로 성립하므로 **기존 "탄약 0 시 자동 장전" 규칙이 재발동**해 다시 장전이 시작된다. 별도의 "장전 취소 후 복구" 로직을 추가할 필요가 없고, 플레이어가 영구적으로 발사 불가 상태에 갇히는 소프트락도 발생하지 않는다(레벨 기획서 3.5의 "소프트락 절대 금지" 원칙과 동일한 취지로 설계).

## 3. 회피 설계

### 3.1 입력

- 회피키: **왼쪽 쉬프트키 / 마우스 우클릭** (원본 고정값, 두 키 모두 동일한 회피 액션으로 처리).
- **설계 결정(기본값)**: `ACombatCharacter::Look`이 `LookAction`과 `MouseLookAction` 두 개의 IA를 같은 처리 함수에 바인딩하는 선례(CombatCharacter.cpp:464-465)를 따라, **신규 제안 `IA_Dodge` 하나에 IMC 레벨에서 좌쉬프트와 우클릭 두 개의 물리 키를 매핑**한다(두 개의 별도 IA를 만들어 동일 함수에 바인딩하는 대안도 가능하나, 하나의 논리 액션으로 묶는 편이 쿨타임/캔슬 로직을 한 곳에서 관리하기 쉽다).

### 3.2 저스트 회피 판정 윈도우 (0~0.4초)

원본 요구사항: "회피키를 누르는 즉시~0.4초 사이에서 저스트 회피 가능". 이를 **회피 모션 재생 시작(입력 시점)부터 0.4초 동안이 무적 프레임(i-frame) 구간이며, 이 구간에 적의 공격 판정이 겹치면 데미지 없이 '저스트 회피'로 처리된다**는 뜻으로 해석해 설계한다(0.4초 이후는 회피 모션의 리커버리 구간으로 무적이 해제되어 피격 가능).

- 구현: `StartDodge()` 시점에 `bIsInvincible = true`로 세팅하고, `FTimerHandle DodgeInvincibilityTimer`를 0.4초로 세팅해 만료 시 `bIsInvincible = false`. `TakeDamage()` 오버라이드(`ACombatCharacter::TakeDamage`의 `CurrentHP <= 0.0f` 조기 반환 가드, CombatCharacter.cpp:381-387과 동일한 자리)에 `if (bIsInvincible) return 0.0f;` 가드를 추가한다.
- **설계 결정(기본값, 추후 조정 가능)**: 저스트 회피 성공(무적 프레임 중 실제로 피격 판정이 걸린 경우) 시 보상으로 짧은 히트스톱(0.15~0.2초 타임 슬로우) 연출과, 다음 1발 한정 데미지 1.5배(설계 결정 수치) 보너스를 부여한다. 원본 요구사항에 명시된 보상은 없으므로 신규 제안이며, 무적 프레임 자체(원본 취지)와 모순되지 않는 범위에서 "반격" 판타지를 강화하는 방향으로 채택했다. 레일건(2장)과 회피를 연결하는 지점이라 오빠의 "힘/전투" 정체성에도 부합한다.

### 3.3 쿨타임 / 사용 가능 상태 / 캔슬 로직

- 쿨타임: **1초** (원본 고정값). 여동생 기획서 3장의 "쿨타임은 시도 시점부터 시작하며 성공/실패 무관하게 소모"와 동일한 관례를 적용해, **회피 입력이 성립한 시점(성공적으로 회피 모션이 시작된 시점)부터 1초 쿨타임을 시작**한다.
- 회피는 **이동, 대기, 공격 모션 중에 사용 가능**(원본 고정값).
- **공격/장전 중 회피 시 캔슬**(원본 고정값): `AnimNotify_EndDash`가 대시 상태 종료를 `EndDash()` 호출로 처리하는 패턴(0장 참고)과 달리, 캔슬은 "몽타주가 끝나길 기다리는" 것이 아니라 **몽타주를 즉시 중단**해야 하므로 아래와 같이 구현한다.

```cpp
void ABrotherCharacter::DoDodgeStart()
{
    // 쿨타임 체크
    if (GetWorld()->GetTimeSeconds() - LastDodgeTime < DodgeCooldown) return;
    if (bIsDodging) return;

    if (UAnimInstance* AnimInstance = GetMesh()->GetAnimInstance())
    {
        if (bIsAttacking)
        {
            // 신규 제안: 발사 몽타주를 짧은 블렌드아웃으로 즉시 중단(공격 캔슬)
            AnimInstance->Montage_Stop(0.1f, FireMontage);
            bIsAttacking = false;
        }
        else if (bIsReloading)
        {
            // 장전 취소: 타이머 클리어 + 장전 몽타주 중단(탄약은 0으로 유지, 2.5절 참고)
            GetWorld()->GetTimerManager().ClearTimer(ReloadTimer);
            AnimInstance->Montage_Stop(0.1f, ReloadMontage);
            bIsReloading = false;
        }
    }

    StartDodge();
}
```

- 회피 모션 종료는 `AnimNotify_EndDash`와 완전히 동일한 패턴으로, **신규 제안 `UAnimNotify_EndDodge`**가 몽타주 끝 프레임에서 `BrotherCharacter->EndDodge()`를 호출해 `bIsDodging = false`로 되돌린다.

### 3.4 상태 요약

| 회피 시도 시점의 상태 | 회피 입력 시 동작 | 캔슬 대상 |
|---|---|---|
| Idle / Move | 즉시 회피 모션 시작 | 없음 |
| Attack(발사 모션 재생 중) | `Montage_Stop`으로 발사 모션 즉시 중단 → 회피 시작 | 공격 캔슬 |
| Reload(장전 중) | `ReloadTimer` 클리어 + 장전 모션 중단 → 회피 시작(탄약 0 유지) | 장전 캔슬 |
| Dodge(회피 중) | 쿨타임(1초)으로 대부분 걸러짐, 쿨타임 내 재입력은 버퍼링 없이 드롭 | 해당 없음 |

```
             좌클릭(탄약>0, !장전, !회피)
   Idle/Move ────────────────────────► Attack(Fire)
       ▲                                    │
       │ 모션 종료(AnimNotify/델리게이트)      │ 탄약=0 도달
       │◄───────────────────────────────────┤
       │                                    ▼
       │                                 Reload(2초)
       │◄────────────────────────────────────┘
       │        타이머 만료(탄약 30 리필)
       │
       │ 회피 입력(쿨타임 완료)
       ▼
     Dodge(0~0.4초 무적) ──► 0.4초~모션 종료(무적 해제, 리커버리) ──► AnimNotify_EndDodge ──► Idle/Move
```

- Attack/Reload 상태에서 회피 입력이 들어오면 위 순환을 기다리지 않고 **즉시 Dodge로 강제 전이**하며, 이때 진행 중이던 Attack/Reload 몽타주는 `Montage_Stop`으로 중단된다(3.3의 표 참고).
- Dodge 상태 자체는 쿨타임(1초)이 재입력을 막으므로 별도의 "Dodge 중 Dodge 캔슬" 케이스는 없다.
- 피격 경직/사망 중 회피 가능 여부는 원본 요구사항에 없는 엣지 케이스다. **설계 결정(기본값)**: 사망 상태에서는 회피를 비활성화한다(ACombatCharacter의 `HandleDeath()`가 이동을 비활성화하는 것과 동일한 취지). 피격 경직 자체를 별도로 둘지는 원본 요구사항에 없으므로 이번 문서 범위에서는 다루지 않는다.

레벨 기획서 3.1절 컨벤션(신규 기능은 기존 `Variant_*`에 섞지 말고, 전용 폴더에 `AI/`, `Animation/`, `Gameplay/`, `Interfaces/`, `UI/` 서브폴더 구조 유지)을 그대로 따른다. `ACombatCharacter`는 0장에서 확인했듯 카메라 방식과 콤보/차지 전용 필드가 이 캐릭터의 요구사항과 맞지 않아 **상속 베이스로 채택하지 않는다**(대신 인터페이스와 AnimNotify 패턴만 재사용). 여동생 기획서가 `Variant_Hacking`이라는 능력 이름 기반 신규 폴더를 제안한 것과 동일한 방식으로, 오빠 쪽도 신규 폴더를 제안한다. 폴더명은 팀 협의로 확정할 것.

## 6. 네트워킹 / 리플리케이션 고려사항 (리슨 서버 기준)

CLAUDE.md의 리슨 서버 전제(호스트가 곧 한 플레이어의 머신)를 따른다. 여동생 기획서 7장과 동일한 "권한 분리 원칙"(입력 반응성은 로컬 즉시 처리, 게임플레이에 영향을 주는 최종 판정은 서버 권위)을 적용하되, 회피는 해킹과 달리 **생존에 직결되는 시간 민감 메커닉**이라는 점에서 온도차를 둔다.

- **레일건 발사**:
  - `CurrentAmmo`(`int32`, `Replicated`), `bIsReloading`(`bool`, `Replicated`)는 서버(호스트)가 권위를 가진다.
  - 흐름: 클라이언트 `Server_RequestFire()` RPC → 서버가 `CurrentAmmo > 0 && !bIsReloading` 재검증 후 라인 트레이스를 서버에서 직접 수행(또는 클라이언트가 보낸 트레이스 결과를 서버가 사거리/시야로 재검증) → `ICombatDamageable::ApplyDamage` 적용 및 `CurrentAmmo` 차감 → `NetMulticast_PlayFireFX()`로 총구 이펙트/피격 이펙트를 전체 클라이언트에 복제.
  - 탄약이 0이 되어 장전이 시작되는 것은 서버 측 `CurrentAmmo` 상태 변화의 자연스러운 결과이므로 **별도의 장전 시작 RPC가 필요 없다** — 여동생 기획서의 해킹 시작 RPC 왕복(`Server_RequestBeginHack`)보다 단순한 흐름이다. `bIsReloading` 복제만으로 모든 클라이언트가 장전 애니메이션/UI를 동기화할 수 있다.
- **회피/무적 프레임**:
  - `bIsDodging`, `bIsInvincible`(둘 다 `Replicated`), `LastDodgeTime`(서버 소유, 여동생 기획서의 `LastHackAttemptTime`과 동일한 패턴)로 관리한다.
  - 클라이언트는 회피 입력 즉시 **로컬에서 회피 모션을 예측 재생**한다(원격 클라이언트가 오빠를 조작하는 경우 RTT 지연이 있으면 회피 판정 지연이 곧 피격으로 직결되는, 매우 체감이 큰 메커닉이기 때문 — 해킹의 "성공/실패 판정 정확성"보다 "즉각 반응성"이 우선). 이후 `Server_RequestDodge()` RPC로 서버가 쿨타임을 재검증해 `bIsDodging`/무적 타이머를 서버 기준으로 확정하고 복제한다.
  - `TakeDamage()`의 무적 가드는 반드시 서버에서 서버가 가진 `bIsInvincible` 값을 기준으로 판정한다(클라이언트 로컬 예측값을 신뢰하지 않는다). 이론상 "화면상으로는 회피했지만 서버 판정 지연으로 데미지가 확정되는" 프레임 단위의 오차가 존재할 수 있으며, 이는 리슨 서버 예측 모델의 일반적 트레이드오프다(레벨 기획서 3.7의 "호스트가 사망 판정 권한을 가진다"는 원칙과 동일선상). 포트폴리오 범위에서는 클라이언트 재보정(리컨실리에이션) 연출까지 구현할 필요는 없다고 명시한다.
- **호스트 자신이 오빠를 조작하는 경우**(리슨 서버 구조상 흔한 케이스)에는 클라이언트=서버이므로 위 지연 문제가 사실상 없다. 원격 클라이언트가 오빠를 조작하는 세션에서만 예측/재검증 흐름이 실제로 의미를 가진다.
- **치트 방지 관점**: 여동생 기획서 7장과 동일하게, 완전한 부정행위 방지까지 과설계하지 않되 "탄약 차감·데미지 확정·무적 판정은 서버가 최종 권한을 가진다"는 원칙만은 지킨다.

## 7. 여동생과의 협동 연계

레벨 기획서 3.5는 "여동생이 해킹하는 동안 오빠가 주변 적을 막아주는 구도를 기본형으로 삼는다(해킹 = 무방비 상태이므로)"를 명시하고 있고, 여동생 기획서 9.3 체크리스트도 "해킹 중인 캐릭터를 다른 캐릭터가 엄호할 수 있는 구조"를 요구한다. 본 문서의 레일건/회피 설계는 이 엄호 관계를 다음과 같이 뒷받침한다.

- **원거리 엄호 적합성**: 여동생의 해킹 감지 반경(`InteractionRadius` 200cm, 여동생 기획서 2.1)은 근접 상호작용 범위라 스스로는 원거리 위협에 대응할 수 없다. 오빠의 레일건은 사거리 3000cm(2.3)의 히트스캔이므로, 여동생이 그로기 미니게임(여동생 기획서 4장) 또는 단말기 해킹(5장)으로 무방비 상태일 때 오빠가 원거리에서 접근 중인 로봇을 선제 저격해 시간을 벌어주는 구도가 자연스럽게 성립한다. 특히 레벨 기획서 3.6의 "원거리 로봇은 조준 레이저로 텔레그래프"되므로, 오빠가 이 텔레그래프를 보고 여동생보다 먼저 반응해 카운터하는 흐름이 만들어진다.
- **역엄호 관계**: 오빠도 장전(2초)·회피 쿨타임(1초) 동안은 스스로 취약해지는 타이밍이 생긴다. 이 타이밍에 여동생이 근접 적을 해킹(5초 그로기, 여동생 기획서 4.3)으로 무력화해 시간을 벌어주는 역방향 엄호도 자연스럽게 성립한다 — 두 캐릭터의 취약 윈도우(오빠: 장전 2초/회피 쿨타임 1초, 여동생: 해킹 쿨타임 3초/해킹 중 무방비)가 서로 다른 타이밍에 위치하므로 서로가 서로의 빈틈을 메꾸는 협동 리듬이 만들어진다.
- 레벨 기획서 3.4의 "두 구간은 반드시 서로가 서로를 도와야 진행 가능하게 짜여야 한다" 원칙과 3.5의 "해킹 = 무방비 상태" 전제를 감안할 때, 실제 맵 배치 시에는 여동생의 해킹 지점 주변에 오빠가 엄호 사격할 수 있는 시야/포지션(엄폐 없는 개활 라인)을 의도적으로 남겨두는 것을 권장한다(맵 담당자와 별도 협의 필요, 본 문서 범위 밖).

## 8. 향후 확장 여지

- **추가 무기**: 레일건 외 보조 무기(예: 근접 강타, 광역 폭발탄 등)를 추가할 경우, `FireRailgun()`과 유사한 별도 함수 + AnimNotify 조합으로 확장 가능하다. 무기 교체가 필요해지면 `TSubclassOf` 기반의 무기 데이터 애셋화(여동생 기획서 5.2의 `TSubclassOf<UHackMinigameBase>` 교체형 구조와 동일한 패턴)를 고려할 수 있다.
- **저스트 회피 연계 스킬**: 3.2의 저스트 회피 보상(데미지 1.5배)을 발판 삼아, 연속 저스트 회피 성공 시 게이지를 쌓아 필살기를 발동하는 식의 확장이 가능하다(원본 요구사항 범위 밖이므로 이번 문서에서는 설계하지 않는다).
- **탄약 픽업**: `Variant_SideScrolling/Gameplay/SideScrollingPickup.h`의 기존 픽업 액터 패턴을 재사용해 맵 곳곳에 탄약 회복 아이템을 배치하는 확장이 가능하다.
- **오빠 전용 구간과의 연동**: 레벨 기획서 3.4의 "파괴 가능한 장애물이 막는 구간"과 연계해, 근접 강타로 장애물을 파괴하는 별도 상호작용을 오빠 전용 패시브로 추가하는 것도 향후 검토 대상이다.

## 9. 완료 체크리스트

### 9.1 공격/레일건

- [ ] 좌클릭 입력 1회당 1회 발사되며(홀드 연사 없음), 탄창이 30발이다.
- [ ] 히트스캔(라인 트레이스) 판정이 `ICombatDamageable::ApplyDamage`로 데미지를 전달한다.
- [ ] 탄약 0 도달 시 자동으로 장전이 시작되고, 장전 중 좌클릭이 무시된다.
- [ ] 장전 딜레이가 2초이며, 만료 시 탄약이 30으로 리필된다.
- [ ] 화면 HUD에 잔여 탄약 수와 장전 중 표시가 나타난다(`URailgunAmmoWidget` 또는 대응 구현).

### 9.2 회피

- [ ] 좌쉬프트 또는 우클릭으로 회피가 발동한다.
- [ ] 회피 입력 시점부터 0.4초간 무적 프레임이 적용되고, 이 구간의 피격이 '저스트 회피'로 처리된다.
- [ ] 회피 쿨타임이 1초이며, 회피 시작 시점부터 소모된다.
- [ ] 이동/대기/공격 모션 중 회피가 정상 발동한다.
- [ ] 공격 중 회피 시 발사 몽타주가 즉시 중단되고(`Montage_Stop`) 회피로 전이된다.
- [ ] 장전 중 회피 시 `ReloadTimer`가 클리어되고 장전이 취소되며, 탄약은 0으로 유지된다(이후 발사 시도 시 자동 재장전 재발동 확인).

### 9.3 상태 머신 / 캔슬

- [ ] Idle/Move ↔ Attack ↔ Reload ↔ Dodge 전이가 4장의 다이어그램대로 동작한다.
- [ ] Attack/Reload 상태에서만 회피가 캔슬을 유발하며, Idle/Move에서는 캔슬 없이 즉시 회피된다.
- [ ] 사망 상태에서는 회피가 발동하지 않는다.

### 9.4 네트워킹

- [ ] `CurrentAmmo`, `bIsReloading`, `bIsDodging`, `bIsInvincible`이 `Replicated`로 선언되어 있다.
- [ ] 발사/데미지 확정이 서버(호스트) 권한으로 처리되고, 클라이언트는 예측 연출만 담당한다.
- [ ] 회피 무적 판정이 서버의 `bIsInvincible` 값을 기준으로 최종 확정된다.
- [ ] 원격 클라이언트가 오빠를 조작하는 경우에도 회피 입력이 로컬에서 즉시 예측 재생된다(RTT 지연 흡수).

### 9.5 협동 정합성

- [ ] 오빠의 사거리/화력이 여동생 해킹 중 엄호에 실질적으로 유효한지(레벨 배치 시) 확인한다.
- [ ] 오빠의 장전/회피 쿨타임 취약 윈도우가 여동생의 그로기 엄호로 보완 가능한 배치인지 확인한다(맵 담당자 협의).
