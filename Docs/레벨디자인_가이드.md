# 에이전트를 위한 레벨 디자인 엔지니어링 가이드

## 1. 문서 목적

이 문서는 Unreal Engine 프로젝트에서 사람, 생성형 AI, 코딩 에이전트가 협업하여 레벨을 설계하고 구현하는 절차를 정의한다.

핵심 목표는 다음과 같다.

- 사람의 기획 의도를 AI가 임의로 왜곡하지 않도록 한다.
- 보기 좋은 배경보다 실제로 이동 가능한 플레이 공간을 먼저 확보한다.
- 플레이어의 실제 크기와 이동 성능을 기준으로 지형의 크기를 결정한다.
- 기존 맵과 에셋을 안전하게 보존한다.
- 레벨 완성 후 사람이 직접 수정한 결과를 후속 자동화 작업이 덮어쓰지 않게 한다.
- 에이전트가 만든 결과를 사람이 Unreal Editor에서 쉽게 검토하고 수정할 수 있게 한다.

> 콘티 이미지는 방향을 전달하는 참고 자료다. 플랫폼 높이, 간격, 충돌 범위까지 보장하는 설계 도면은 아니다. 최종 수치는 반드시 게임 프로젝트의 실제 플레이어 데이터를 기준으로 다시 계산해야 한다.

---

## 2. 전체 작업 흐름

```text
사람이 맵 기획 초안 작성
        ↓
AI를 이용해 기획안 구체화 및 Markdown 문서화
        ↓
사람이 구체화된 기획서를 직접 검토
        ↓
기획서를 바탕으로 레벨 디자인 콘티 이미지 생성
        ↓
기획서 + 콘티 + 프로젝트 정보를 코딩 에이전트에 전달
        ↓
플레이어 실측 및 이동 가능 구간 설계
        ↓
신규 레벨에 오브젝트 제작·배치
        ↓
저장 후 재로딩 검사 및 실제 플레이 테스트
```

---

## 3. 1단계: 사람이 맵 기획 초안 작성

가능하면 최초 초안은 사람이 직접 작성한다. AI가 처음부터 모든 내용을 결정하게 하면 게임 전체의 맥락, 전후 레벨과의 연결, 플레이 의도가 약해질 수 있다.

초안에는 최소한 다음 항목을 포함한다.

### 3.1 기본 정보

- 맵 이름과 지역
- 게임 시점: 2D, 2.5D, 3D 등
- 시작 지점과 최종 목적지
- 맵을 통과해야 하는 서사적 이유
- 예상 플레이 시간

### 3.2 플레이 구조

- 맵을 구성하는 주요 구간
- 각 구간에서 새로 소개되는 행동이나 기믹
- 전투, 탐색, 플랫폼 이동, 퍼즐 등의 비중
- 난이도와 긴장감의 변화
- 실패하거나 추락했을 때의 복귀 방식

### 3.3 아트 방향

- 장소와 시대적 배경
- 핵심 분위기와 디자인 키워드
- 주요 색상과 조명 방향
- 반복해서 등장할 랜드마크
- 플레이 가능한 지형과 배경 장식의 시각적 구분 방법

초안 단계에서 정확한 Unreal 좌표나 플랫폼 치수를 결정할 필요는 없다. 이 단계에서는 “플레이어가 무엇을 보고, 무엇을 판단하고, 어떤 행동을 하게 할 것인가”를 명확히 하는 것이 중요하다.

---

## 4. 2단계: AI를 활용한 기획안 구체화 및 문서화

초안을 생성형 AI에 전달하여 Markdown 형식의 구체적인 레벨 기획서로 확장한다.

기획서는 일반적인 분위기 설명에 그치지 않고 다음 내용을 포함해야 한다.

- 맵 개요와 최종 목표
- 구역별 역할과 공간 구성
- 구역별 핵심 오브젝트
- 플레이어의 주 동선과 선택 동선
- 전투 및 기믹의 배치 의도
- 난이도와 페이싱 변화
- 랜드마크와 시선 유도 방법
- 색상, 조명, 재질 방향
- 클리어 조건과 다음 레벨 연결 방식
- 구현 범위와 미구현 기능의 구분

각 구역은 다음 형식으로 작성하면 좋다.

```markdown
## 구간 이름

### 역할
이 구간이 전체 레벨에서 담당하는 기능

### 공간 구성
지형, 높이 변화, 배경, 이동 경로

### 주요 요소
적, 기믹, 플랫폼, 상호작용 오브젝트

### 플레이 의도
플레이어가 관찰하고 판단하고 실행해야 하는 행동

### 진입 및 이탈 조건
앞 구간과 연결되는 위치, 다음 구간으로 넘어가는 조건
```

결과 문서는 프로젝트의 `Docs/` 폴더에 저장한다.

예시:

```text
Docs/Map1_레벨디자인_기획안.md
Docs/Map2_레벨디자인_기획안.md
```

## 5. 3단계: 사람이 기획서를 직접 검토

이 단계는 생략하면 안 된다. AI가 작성한 문서는 문장 자체는 자연스러워도 실제 플레이 흐름이 모순되거나 프로젝트에 없는 기능을 전제로 할 수 있다.

다음 질문을 기준으로 검토한다.

- 플레이어의 목표가 처음부터 끝까지 명확한가?
- 각 구간의 역할이 서로 중복되지 않는가?
- 난이도가 갑자기 상승하거나 의미 없이 반복되지 않는가?
- 프로젝트에 없는 기능을 필수 동선에 사용하지 않았는가?
- 벽 점프, 대시, 매달리기 등 실제 구현 여부가 불확실한 능력을 가정하지 않았는가?
- 선택 경로가 막다른 길이 되지 않는가?
- 기믹 성공 전후의 상태 변화가 명확한가?
- 맵의 클리어 조건이 구현 가능한 형태인가?
- 다음 레벨과 연결되는 위치와 연출이 정의되어 있는가?

모호한 표현은 에이전트에게 넘기기 전에 수정한다.

나쁜 예:

```text
적당히 어려운 플랫폼 구간을 만든다.
```

좋은 예:

```text
타워 외벽에서 위쪽으로 이동한다. 벽 점프는 필수로 사용하지 않으며,
기본 점프로 도달 가능한 정비 발판과 정지된 스크랩 리프트를 연속 배치한다.
```

## 6. 4단계: 레벨 디자인 콘티 이미지 생성

검토가 끝난 기획서를 바탕으로 레벨 디자인 콘티 이미지를 생성한다.

콘티에는 가능한 한 다음 요소를 표시한다.

- 전체 레벨의 사이드뷰 또는 탑뷰
- START와 EXIT 위치
- 구간 번호와 구간명
- 주 동선과 선택 동선 화살표
- 주요 높이 변화
- 랜드마크와 핵심 기믹
- 적 또는 위험 요소의 대략적인 위치
- 플레이어 실루엣을 이용한 크기 비교
- 구역별 대표 색상과 조명
- 주요 오브젝트의 상세 확대 컷

콘티 이미지 생성 요청 예시:

```text
첨부한 레벨 기획서를 바탕으로 2.5D 사이드뷰 레벨 디자인 콘티를 제작해줘.
전체 맵을 한눈에 볼 수 있는 횡단면을 중심으로 구성하고,
START/EXIT, 구역명, 진행 화살표, 높이 변화, 핵심 기믹과 랜드마크를 표시해줘.
플레이어 실루엣을 배치해 구조물과 발판의 크기 비율을 비교할 수 있게 해줘.
하단에는 구역별 상세 컷과 주요 플레이 의도를 정리해줘.
```

콘티가 멋있게 보이더라도 그대로 구현 가능한 것은 아니다. 다음 항목은 실제 제작 전에 다시 확인해야 한다.

- 점프 높이와 발판 간격
- 캐릭터가 통과할 수 있는 천장 높이
- 카메라에 가려지는 전경 오브젝트
- 충돌이 필요한 오브젝트와 장식물
- 실제로 구현된 플레이어 능력

## 7. 5단계: 코딩 에이전트에 레벨 구현 요청

Codex, Claude Code 등의 코딩 에이전트에는 최소한 다음 자료를 함께 전달한다.

1. 검토가 끝난 레벨 기획서 Markdown 파일
2. 레벨 디자인 콘티 이미지
3. 작업할 Unreal 프로젝트 경로
4. 목표 레벨 이름
5. 사용할 플레이어 블루프린트 또는 C++ 클래스
6. 기존 에셋 사용 여부
7. 구현 범위와 제외 범위

### 7.1 안전을 위한 기본 요청

가능하면 기존 레벨을 바로 덮어쓰지 않고 새로운 레벨이나 씬에 제작하도록 요청한다.

예시:

```text
기존 Map1은 수정하지 말고 Map1_Rework라는 신규 레벨을 생성해 작업해줘.
기존 맵이 에디터에서 열려 있으면 강제로 덮어쓰거나 에디터를 종료하지 마.
필요하면 결과를 별도 맵으로 저장해줘.
```

이 방식의 장점은 다음과 같다.

- 기존 작업을 잃을 위험이 적다.
- 원본과 결과물을 쉽게 비교할 수 있다.
- 파일 잠금으로 인한 저장 실패를 피하기 쉽다.
- 결과가 마음에 들지 않을 때 신규 레벨만 제거하면 된다.

### 7.2 기존 수정사항 보존 요청

이미 한 번 제작된 레벨을 에이전트에게 다시 수정시킬 때는 **작업을 시작하기 전에 현재 맵에 사람의 수정사항이 있는지 반드시 확인**하도록 요청한다.

코드 기반 생성기는 기존 액터를 모두 삭제한 뒤 처음부터 다시 만드는 방식으로 작성되는 경우가 많다. 이 생성기를 그대로 재실행하면 사람이 직접 조정한 위치, 크기, 머티리얼, 조명, 충돌과 추가 오브젝트가 모두 사라질 수 있다.

따라서 수정 작업에는 다음 원칙을 적용한다.

- 현재 맵과 최초 생성 결과 또는 이전 작업 기록을 비교한다.
- 사람이 직접 수정한 액터와 속성은 사용자 소유 데이터로 취급한다.
- 누가 수정했는지 확실하지 않은 대상도 사용자 소유로 간주한다.
- 사용자가 요청한 액터와 속성만 추가하거나 변경한다.
- 요청 범위 밖의 액터는 이동, 삭제, 재생성, 이름 변경, 폴더 이동 또는 머티리얼 교체를 하지 않는다.
- 에이전트가 과거에 생성한 액터라도 사람이 이후 수정했다면 삭제하거나 초기값으로 되돌리지 않는다.
- 전체 재생성이 필요한 경우 기존 맵을 덮어쓰지 말고 별도 레벨을 만들거나 먼저 사용자 승인을 받는다.

요청 예시:

```text
작업 전에 현재 맵을 검사해서 이전 생성 이후 사람이 수정한 액터와 속성을 식별해줘.
사람이 수정했거나 소유자가 불명확한 대상은 절대 초기화하거나 재생성하지 마.
이번 요청에서 지정한 액터와 속성만 증분 수정하고 나머지 맵 상태는 그대로 보존해줘.
기존 액터 전체 삭제 후 재생성하는 생성기는 실행하지 마.
변경 전후의 비대상 액터 상태가 동일한지도 검증해줘.
```

### 7.3 플레이어 비율 확인 요청

에이전트가 임의의 사람 크기를 가정하지 않게 해야 한다. 프로젝트의 실제 플레이어 에셋에서 다음 값을 읽도록 요청한다.

- Capsule Radius
- Capsule Half Height
- Skeletal Mesh 크기와 상대 위치
- Max Walk Speed
- Jump Z Velocity
- Gravity Scale 및 실제 Gravity Z
- Air Control
- 이동 평면 제약
- 카메라 거리, FOV, Projection Mode
- 벽 점프, 대시, 매달리기 등 특수 이동 능력의 실제 구현 여부

### 7.4 이동 성능 계산

기본 점프의 이론상 최고 상승량은 다음 식으로 계산할 수 있다.

```text
점프 최고 상승량 = JumpZVelocity² / (2 × |GravityZ|)
```

동일한 높이로 착지할 때의 이론상 체공 시간은 다음과 같다.

```text
체공 시간 = 2 × JumpZVelocity / |GravityZ|
```

이론상 수평 이동 거리는 다음과 같이 추정할 수 있다.

```text
수평 이동 거리 = 이동 속도 × 체공 시간
```

다만 실제 플레이에서는 가속 시간, 공중 제어, 조작 오차, 발판 모서리와 캡슐 크기가 영향을 준다. 따라서 최대 이론값을 그대로 사용하지 말고 보수적인 안전 계수를 적용해야 한다.

권장 원칙:

- 필수 동선은 최대 이론값보다 충분히 짧게 설계한다.
- 상승 점프는 최고 상승량에 가깝게 배치하지 않는다.
- 공중 제어가 낮다면 점프 직전 달릴 공간을 제공한다.
- 착지 발판은 캐릭터 캡슐보다 충분히 넓게 만든다.
- 어려운 최대 거리 점프는 선택 경로나 후반 도전 구간에만 사용한다.
- 벽 점프가 구현되어 있지 않다면 필수 동선에서 절대 요구하지 않는다.

## 8. 에이전트의 권장 구현 순서

### 8.1 사전 조사

에이전트는 배치 작업 전에 다음을 확인해야 한다.

- 프로젝트와 Unreal Engine 버전
- 플레이어 클래스와 GameMode
- 이동 입력이 사용하는 월드 축
- 플레이어 캡슐과 점프 성능
- 카메라 시점과 화면에 보이는 범위
- 기존 레벨과 에셋의 파일 잠금 여부
- 프로젝트에서 사용할 수 있는 메시와 머티리얼

### 8.2 기존 맵 변경사항 감사 및 증분 패치

기존 레벨을 수정하는 작업에서는 배치나 생성보다 변경사항 감사가 먼저다. 감사를 완료할 수 없으면 작업을 중단하고 사용자에게 현재 맵을 보존한 새 사본에서 작업할지 확인한다.

#### 변경 전 스냅샷

작업 전에 맵을 백업하고, 가능한 경우 액터 상태를 JSON 등의 텍스트 형식으로 기록한다.

권장 기록 항목:

- 액터 경로 또는 안정적으로 식별 가능한 이름
- Actor Label과 Folder Path
- 클래스와 태그
- Location, Rotation, Scale
- Static Mesh와 Skeletal Mesh 참조
- 머티리얼 슬롯
- 충돌 프로파일과 Collision Enabled 상태
- 가시성, 모빌리티와 주요 컴포넌트 설정
- 부모·자식 또는 Attach 관계

`.umap`은 바이너리 파일이므로 Git diff만으로 사람이 수정한 내용을 충분히 판단하기 어렵다. 에이전트가 처음 레벨을 생성할 때 위 정보를 담은 생성 결과 manifest를 함께 남겨두면 다음 수정 때 현재 상태와 비교하기 쉽다.

#### 소유권 분류

현재 액터와 속성을 다음처럼 분류한다.

| 분류 | 처리 원칙 |
|---|---|
| 사람이 추가하거나 수정한 대상 | 요청에 명시되지 않으면 변경 금지 |
| 에이전트가 생성했고 이후 변경되지 않은 대상 | 요청 범위 안에서만 수정 가능 |
| 사람과 에이전트가 함께 수정한 대상 | 사람의 현재 값을 우선 보존 |
| 출처를 판단할 수 없는 대상 | 사용자 소유로 간주하고 변경 금지 |
| 이번 요청에서 명시한 대상 | 지정된 속성만 최소 범위로 수정 |

에이전트 전용 태그나 폴더 안에 있다는 이유만으로 삭제 권한이 생기는 것은 아니다. 해당 액터가 최초 생성 이후 변경되었다면 사람의 수정사항을 우선한다.

#### 증분 수정 규칙

- `destroy all`, 폴더 전체 삭제, 생성 태그 전체 삭제 후 재생성 같은 동작을 금지한다.
- 액터는 정확한 이름, 경로, 태그와 클래스 조건으로 좁혀 선택한다.
- 가능한 경우 액터 전체를 교체하지 말고 요청된 속성만 패치한다.
- 새 오브젝트는 별도 폴더와 명확한 태그를 사용해 추가한다.
- 기존 Actor Label과 참조 경로를 불필요하게 변경하지 않는다.
- Level Sequence, Blueprint, Trigger 등이 참조하는 액터를 삭제하거나 교체하기 전에 참조 관계를 확인한다.
- 재생성이 꼭 필요한 구역은 기존 맵 사본에서 먼저 생성하고 사람이 비교할 수 있게 한다.
- 요청 범위를 넘어서는 정리, 리팩터링, 자동 정렬과 스타일 통일을 함께 수행하지 않는다.

#### 변경 후 비대상 불변 검증

수정 후에는 변경 전 스냅샷과 다시 비교한다.

- 요청 대상 액터는 요청된 속성만 바뀌었는가?
- 비대상 액터의 Transform, Mesh, Material과 Collision이 그대로인가?
- 사람의 신규 액터가 삭제되지 않았는가?
- 액터 수가 예상하지 못하게 감소하지 않았는가?
- 기존 참조와 Attach 관계가 유지되는가?

비대상 변경이 발견되면 결과를 저장 완료로 간주하지 말고 해당 변경을 되돌리거나 사용자에게 보고한다.

### 8.3 필수 동선 설계

아트 오브젝트보다 먼저 START에서 EXIT까지 이어지는 필수 동선을 수치로 정의한다.

각 발판에 다음 정보를 기록하는 것이 좋다.

```text
발판 이름
시작 좌표와 끝 좌표
표면 높이
이전 발판과의 수평 간격
이전 발판 대비 높이 차이
점프 도달 가능 여부
```

필수 동선이 검증된 뒤 선택 경로, 전투 공간, 은폐물과 장식을 추가한다.

### 8.4 오브젝트 제작과 배치

“그레이박싱이 아닌 완성형 오브젝트”를 요청할 때는 원하는 수준을 명확히 한다.

에이전트가 제작할 수 있는 형태의 예시는 다음과 같다.

- 기본 도형과 프로젝트 메시를 조립한 다중 부품 산업 오브젝트
- 전용 머티리얼과 발광 재질
- 배관, 난간, 지지대, 볼트, 케이블 등의 디테일
- 조립식 스크랩 구조물
- 타워, 해킹 장치, 게이트, 드론 등의 복합 프롭

단순히 Cube를 크게 늘리고 색만 바꾼 결과는 완성형 오브젝트로 간주하지 않는다. 실루엣, 기능적 구조, 재질 구분과 작은 디테일을 함께 구성해야 한다.

반대로 에이전트가 여러 기본 메시를 조립한 오브젝트는 하나의 신규 Static Mesh 에셋과 같지 않다. 결과물을 실제 단일 메시, Blueprint Actor 또는 재사용 가능한 모듈 에셋으로 만들 필요가 있다면 요청에 명시한다.

### 8.5 충돌 분리

충돌은 플레이 가능한 지형에만 명시적으로 적용한다.

권장 분류:

| 종류 | 권장 충돌 |
|---|---|
| 바닥 및 필수 발판 | BlockAll 또는 프로젝트 전용 프로파일 |
| 플레이어가 올라갈 수 있는 상자 | 의도에 맞는 Blocking Collision |
| 배경 타워와 도시 실루엣 | NoCollision |
| 난간, 케이블, 볼트, 간판 | 일반적으로 NoCollision |
| 전경 장식 | NoCollision |
| 트리거 및 상호작용 범위 | Query Only 또는 전용 프로파일 |

장식물에 기본 `BlockAll`이 남아 있으면 보이지 않는 벽, 이동 방해, 발사체 충돌 등의 문제가 발생할 수 있다.

### 8.6 아트와 조명 적용

이동 가능성이 확보된 뒤 다음 요소를 적용한다.

- 구역별 색상 대비
- 위험 요소를 나타내는 경고색
- 목표 지점을 유도하는 발광 재질
- 배경, 중경, 전경의 깊이 분리
- 플레이어와 발판의 명암 대비
- 시야를 가리지 않는 전경 오브젝트
- 카메라 충돌과 줌 변화 여부

## 9. Unreal 작업 방식 선택

코딩 에이전트가 Unreal을 수정하는 방식은 환경에 따라 달라진다.

### 9.1 별도 명령줄 에디터 방식

```text
UnrealEditor-Cmd.exe
  → 프로젝트 로드
  → Python 스크립트 실행
  → 에셋 및 맵 저장
```

장점:

- Remote Execution을 켜지 않아도 사용할 수 있다.
- 반복 생성과 검증을 자동화하기 좋다.
- 마우스 자동화보다 빠르고 재현성이 높다.

주의점:

- 실행 중인 에디터가 같은 에셋을 열고 있으면 파일 잠금으로 저장이 실패할 수 있다.
- 실행 중인 에디터 화면에 변경 사항이 즉시 반영되지 않을 수 있다.
- 작업 전 백업과 신규 레벨 사용이 중요하다.

### 9.2 Unreal Python Remote Execution 방식

현재 실행 중인 Unreal Editor 세션에서 Python 코드를 실행한다.

장점:

- 현재 열려 있는 레벨과 선택된 액터를 바로 조작할 수 있다.
- 별도 프로세스 간 파일 잠금 문제를 줄일 수 있다.
- 결과를 에디터에서 즉시 확인하기 쉽다.

필요한 경우 다음 설정을 켠다.

```text
Edit → Project Settings → Plugins → Python → Enable Remote Execution
```

### 9.3 화면 및 마우스 자동화 방식

직접 클릭과 드래그로 에디터를 조작하는 방식이다. 다른 방법이 없을 때만 사용한다.

단점:

- 느리고 해상도와 UI 배치에 영향을 받는다.
- 대규모 액터 배치에 적합하지 않다.
- 좌표와 값의 재현성이 낮다.

## 10. 검증 절차

에이전트가 “저장 완료”라고 출력한 것만으로 작업이 끝난 것은 아니다.

### 10.1 자동 검증

별도 Unreal 프로세스에서 저장된 맵을 다시 열어 다음을 확인한다.

- 맵이 오류 없이 로드되는가?
- 예상한 GameMode와 Default Pawn이 연결되어 있는가?
- PlayerStart가 올바른 위치에 하나만 존재하는가?
- 필수 발판이 모두 존재하는가?
- 모든 필수 점프가 계산상 도달 가능한가?
- 장식물에 불필요한 충돌이 남아 있지 않은가?
- 생성된 머티리얼과 메시 참조가 유효한가?
- START, 주요 구역, EXIT 대표 오브젝트가 모두 존재하는가?
- 원본 맵과 원본 에셋이 의도치 않게 수정되지 않았는가?

### 10.2 사람의 플레이 테스트

자동 계산은 실제 조작감을 완전히 대신할 수 없다. Unreal Editor에서 직접 플레이하며 다음을 확인한다.

- 시작 지점에서 종료 지점까지 실제로 이동 가능한가?
- 달리기 공간 없이 최대 거리 점프를 요구하지 않는가?
- 천장이나 장식물에 캐릭터가 걸리지 않는가?
- 플랫폼의 앞뒤 깊이 때문에 화면 밖으로 떨어지지 않는가?
- 카메라가 벽과 전경 오브젝트에 가려지지 않는가?
- 점프 착지 시 충돌면 중복으로 떨림이 발생하지 않는가?
- 플레이 가능한 지형이 배경 장식과 시각적으로 구분되는가?
- 목표 방향을 별도 설명 없이 알아볼 수 있는가?

문제가 발견되면 “점프가 어렵다”처럼 표현하지 말고 구체적인 위치와 증상을 기록한다.

예시:

```text
구간 3의 Climb05 → Climb06 이동 시 상승 높이는 괜찮지만,
도약 전에 달릴 공간이 부족해 정지 상태에서는 착지하기 어렵다.
Climb05의 폭을 150uu 늘리거나 간격을 40uu 줄여야 한다.
```

## 11. 에이전트 요청문 템플릿

```markdown
첨부 자료를 참고해 Unreal Engine 레벨을 제작해줘.

## 참고 자료
- 기획서: `Docs/Map1_레벨디자인_기획안.md`
- 콘티 이미지: 첨부 이미지
- 플레이어: `/Game/.../BP_Player`

- 기존 에셋을 덮어쓰기 전에 백업할 것
- 에디터에서 파일이 잠겨 있으면 강제로 종료하거나 덮어쓰지 말 것
- 기존 레벨의 수정 작업이라면 실행 전에 현재 액터 상태를 감사하고 변경 전 스냅샷을 남길 것
- 최초 생성 결과와 현재 맵을 비교해 사람이 수정한 액터와 속성을 식별할 것
- 사람이 수정했거나 소유자가 불명확한 대상은 사용자 소유로 간주할 것
- 기존 액터 전체 삭제 후 재생성하는 방식은 사용하지 말 것
- 이번 요청에 명시된 대상과 속성만 증분 수정하고 나머지는 변경하지 말 것

## 플레이 조건
- 플레이어의 Capsule, JumpZVelocity, Gravity, MaxWalkSpeed, AirControl을 실제 에셋에서 읽을 것
- 필수 동선의 모든 점프 높이와 간격을 수치로 검증할 것
- 프로젝트에 구현되지 않은 벽 점프나 대시를 필수 동선에 사용하지 말 것
- START부터 EXIT까지 기본 이동과 점프만으로 통과 가능한 경로를 확보할 것

## 제작 조건
- 단순 그레이박싱이 아니라 콘티의 테마에 맞는 다중 부품 오브젝트와 전용 머티리얼을 제작할 것
- 플레이 지형과 배경 장식의 충돌을 분리할 것
- 배경, 중경, 전경을 구성하되 플레이어와 필수 발판을 가리지 말 것
- 기획서의 구간 구성을 레벨 폴더와 액터 이름에 반영할 것

## 검증 조건
- 저장된 맵을 별도 프로세스에서 재로딩할 것
- GameMode, PlayerStart, 머티리얼 참조, 충돌 개수와 필수 오브젝트 존재 여부를 검사할 것
- 플레이어 이동 수치와 필수 점프별 안전 여유를 결과에 보고할 것
- 구현하지 않은 AI, 퍼즐, 이동 플랫폼 등의 기능은 명확히 구분해 보고할 것
- 변경 전후 스냅샷을 비교해 비대상 액터와 사람이 수정한 속성이 보존됐는지 검사할 것
- 실제로 추가·수정·삭제한 액터와 속성만 목록으로 보고할 것
```

- [ ] 기존 레벨 수정 전 액터와 주요 속성 스냅샷을 생성했다.
- [ ] 최초 생성 결과와 현재 맵의 차이를 검사했다.
- [ ] 사람이 수정한 대상과 소유자가 불명확한 대상을 사용자 소유로 분류했다.
- [ ] 전체 삭제 후 재생성하지 않고 요청 범위만 증분 수정했다.
- [ ] 요청하지 않은 정리, 이름 변경, 폴더 이동과 머티리얼 교체를 하지 않았다.

### 검증

- [ ] 저장된 맵을 다시 열어 로드 오류가 없는지 확인했다.
- [ ] GameMode와 Default Pawn 연결을 확인했다.
- [ ] 불필요한 충돌이 없는지 확인했다.
- [ ] 머티리얼과 메시 참조가 유효하다.
- [ ] 사람이 직접 플레이 테스트를 완료했다.
- [ ] 미구현 기믹과 후속 작업이 문서화되어 있다.
- [ ] 변경 전후 비교에서 비대상 액터와 속성이 동일하다.
- [ ] 사람의 수동 수정사항이 모두 보존됐다.
- [ ] 추가·수정·삭제된 대상의 최종 목록을 검토했다.

## 13. 핵심 원칙 요약

1. 사람의 초안과 검토를 작업의 기준으로 삼는다.
2. 콘티는 시각적 방향이며 실제 치수는 플레이어 데이터로 결정한다.
3. 아트보다 먼저 START에서 EXIT까지 이동 가능한 경로를 확보한다.
4. 기존 맵 대신 신규 레벨에서 작업하는 것이 안전하다.
5. 필수 동선에 미구현 능력을 요구하지 않는다.
6. 장식물과 플레이 지형의 충돌을 분리한다.
7. 저장 후 반드시 새 프로세스에서 재로딩 검사를 한다.
8. 자동 검증 이후에도 사람이 직접 플레이해야 한다.
9. 기존 레벨 수정 전에는 사람의 변경사항을 먼저 감사하고 백업한다.
10. 수정 요청은 전체 재생성이 아니라 요청 범위만 다루는 증분 패치로 수행한다.
11. 사람이 수정했거나 출처가 불분명한 데이터는 사용자 소유로 간주해 변경하지 않는다.
12. 작업 후 비대상 액터가 그대로인지 변경 전후 스냅샷으로 검증한다.
